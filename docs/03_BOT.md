# 03. Telegram Bot

## Назначение

Telegram-бот нужен менеджерам салонов для оформления заявок на замеры.

Бот должен:

* авторизовать менеджера;
* понять его салон и manager_id;
* собрать заявку;
* применить правила салона;
* сформировать карточку;
* сохранить заявку;
* отправить подтверждённую карточку в рабочий Telegram dispatch-чат, если он настроен.

## Запуск

Бот запускается вместе с приложением через:

```bash
npm run dev
```

Используется Telegraf long polling.

Webhook в MVP не используется.

Для локального тестирования Telegram flow используется отдельный dev-бот `@zamerflow_dev_bot` и отдельный dev `BOT_TOKEN`.

Production-бот не используется для локального тестирования. Локальный `.env` должен содержать dev token и локальный `DATABASE_PATH`, например `./data/zamerflow-dev.sqlite`. Production-сервис на VPS при этом не нужно останавливать.

Если нужно проверить только админку без Telegram long polling, можно поставить `BOT_ENABLED=false`.

При запуске long polling бот может отбрасывать pending updates после простоя процесса. Это MVP-компромисс: сообщения и кнопки, отправленные во время простоя, могут быть потеряны, но старые callback updates после рестарта не должны ронять процесс.

## Команды

### `/start`

В личном чате:

* проверяет, привязан ли Telegram-пользователь к менеджеру;
* если пользователь уже авторизован, показывает его менеджера и салон;
* если нет — просит ввести одноразовый код доступа.

В группе:

* сообщает, что для оформления заявки нужно использовать `/new` и отвечать reply-сообщениями.

### `/new`

Запускает создание новой заявки.

Если пользователь не авторизован, бот просит сначала пройти `/start`.

Если пользователь авторизован как менеджер или директор салона, бот:

* берёт салон из `telegram_users`;
* берёт менеджера из `telegram_users`;
* не спрашивает выбор салона;
* создаёт черновик сразу с salon/manager snapshot.

Для других ролей или будущего оператора может быть доступен выбор активного салона из списка.

### `/whoami`

Показывает авторизованному менеджеру пользовательский профиль:

* имя менеджера из `salon_managers`;
* салон из связанной записи `salons`;
* человекочитаемую роль, например "менеджер";
* контактный телефон менеджера.

Технические поля вроде `telegram_user_id`, username, внутренних id и технических ролей в обычном выводе не показываются.

### `/chatid`

Диагностическая команда для получения Telegram `chat_id` текущего чата.

Используется, чтобы получить `DISPATCH_CHAT_ID` рабочего группового чата для отправки подтверждённых карточек заявок.

Для dispatch-flow нужен chat id группы или супергруппы, а не личного чата пользователя с ботом.

### `/cancel`

Отменяет текущую заявку и удаляет in-memory черновик.

## Авторизация менеджера

Менеджер авторизуется через одноразовый код доступа.

Код хранится в `manager_auth_codes` и связан с `manager_id`.

Flow:

```text
/start
→ бот проверяет telegram_users
→ если привязки нет, просит код
→ менеджер вводит код
→ бот ищет неиспользованный код
→ проверяет активного менеджера и активный салон
→ создаёт telegram_users
→ помечает код использованным
```

Код после успешного использования становится `is_used = 1`.

## Черновики

Черновики заявок хранятся in-memory.

Ключ черновика строится по Telegram chat id и user id.

Следствие: при рестарте процесса незавершённые черновики теряются. Для MVP это допустимо.

Старые inline-кнопки после рестарта считаются best-effort: если Telegram уже не принимает callback acknowledgement, бот не должен падать. Пользователь может получить сообщение "Черновик не найден. Начните новую заявку через /new." или начать новую заявку вручную.

## Основной flow заявки

Для авторизованного менеджера бот показывает прогресс основных вопросов в том же сообщении, что и вопрос:

```text
Шаг N из M
Текст вопроса
```

Основные вопросы стандартного `/new` flow:

1. Контакт клиента или представителя — номер телефона, имя.
2. Точный адрес клиента с населённым пунктом.
3. Метро / ориентир.
4. Дата замера.
5. Желаемое время прибытия замерщика.
6. Позиции под замер.
7. Кто оплачивает, если оплата не фиксирована салоном.
8. Доплаты / особенности.
9. Комментарий.

Если вопрос оплаты задаётся, бот показывает прогресс от `Шаг 1 из 9` до `Шаг 9 из 9`.
Если оплата уже определена правилом салона, вопрос оплаты не показывается, а прогресс идёт от `Шаг 1 из 8` до `Шаг 8 из 8`.

Необязательные основные вопросы входят в счётчик, если они показываются пользователю, даже когда их можно пропустить: метро / ориентир, желаемое время, доплаты / особенности и комментарий.
После пропуска необязательного вопроса следующий вопрос показывает следующий номер основного шага.

Выбор позиций под замер считается одним основным шагом. Добавление нескольких позиций и ручной ввод позиции не увеличивают счётчик: `manualServiceItem` остаётся подшагом "Позиции под замер" и показывает тот же номер шага.

Не входят в счётчик основных вопросов:

* автоматически определённые салон и менеджер;
* добавление фотографий, проекта или плана помещения;
* предпросмотр карточки;
* принятие заявки.

На шаге контакта клиента менеджер может вводить российский телефон с пробелами, скобками и дефисами.
Если в тексте есть телефон, бот нормализует его к формату `+7-XXX-XXX-XX-XX` перед сохранением заявки.
Если вместе с телефоном введено имя или пояснение, оно сохраняется вместе с нормализованным телефоном, например `89209144098 Виктория` превращается в `+7-920-914-40-98 Виктория`.
Свободный текст без телефона сохраняется как введён.
Явно некорректный телефон, например `89094` или неполный номер после `+7`, не сохраняется: бот просит исправить контакт.

После предпросмотра:

```text
Предпросмотр
→ Принять
→ сохранить заявку
→ отправить карточку в dispatch-чат
→ показать менеджеру результат
```

Если `DISPATCH_CHAT_ID` не настроен или Telegram не принял сообщение, заявка всё равно сохраняется со статусом `awaiting_coordination` и history event `created`, а менеджер получает подтверждение приёма заявки и предупреждение, что dispatch-отправка не удалась.

После даты есть optional step:

```text
Дата замера? Пример: "18 октября" или "18.10.2026".
→ Желаемое время прибытия замерщика? Можно пропустить.
→ Позиции под замер.
```

Шаг даты остаётся основным шагом с тем же progress-префиксом `Шаг N из M`. Количество и порядок основных шагов не меняются: после успешно принятой даты бот всегда переходит на существующий шаг `measureTime`.

На шаге даты доступна кнопка `По договорённости`. При выборе кнопки бот сохраняет в `measureDate` каноническое значение `По договорённости` и переходит к вопросу желаемого времени. Это работает как в личном чате через reply-клавиатуру, так и в группе через inline-кнопку рядом с reply-вопросом.

Бот распознаёт чистый ввод даты в форматах:

```text
18 октября
18 октября 2026
18.10
18.10.26
18.10.2026
```

Названия месяцев распознаются без учёта регистра. Для чистой распознаваемой даты бот проверяет календарную корректность: например, `18.10.2026` и `29.02.2028` принимаются, а `31.02.2026`, `29.02.2026`, `32 октября`, `18.13.2026` и `00.10.2026` отклоняются. Даты в прошлом не запрещаются. Если год не указан, бот проверяет день и месяц без привязки к конкретному году, поэтому `29 февраля` допустимо.

Корректная распознаваемая дата перед сохранением нормализуется в человекочитаемый русский формат:

```text
18.10 → 18 октября
18.10.26 → 18 октября
18.10.2026 → 18 октября
18.10.2027 → 18 октября 2027
```

Если явно указан текущий календарный год, он не сохраняется в тексте даты. Если явно указан другой год, он сохраняется. Двузначный год трактуется как `20YY` только для проверки и нормализации.

Свободный и смешанный текст сохраняется без изменения, если всё значение целиком не является одной поддерживаемой чистой датой:

```text
после готовности кухни
ориентировочно конец октября
28.09.26 или по договорённости
```

Бот не извлекает дату из смешанного текста и не валидирует отдельные фрагменты свободного текста.

Текст вопроса для менеджера короткий: `Желаемое время прибытия замерщика? Можно пропустить.`

Бот не парсит и не нормализует желаемое время. Если время заполнено, первая строка карточки получает время после даты и `❗`, например `*На 29 июня* утром ❗`. Жирным шрифтом выделяется только дата, время остаётся обычным текстом. Если время не заполнено, формат остаётся прежним: `*На 01 июля*`. Для специального значения даты `По договорённости` первая строка карточки не содержит слово `На`: без времени выводится `*По договорённости*`, с желаемым временем — `*По договорённости* после 16:00 ❗`.

В вопросе оплаты кнопки показываются в именительном падеже: "клиент", "салон", "депозит", "с ИП на самозанятого". В карточке после "Оплата" используется форма для карточки из справочника, например "клиентом", "салоном", "депозитом".

## Фотографии заявки

После комментария бот спрашивает:

```text
Есть фото / проект / план помещения?

Отправьте до 5 фотографий.
Когда закончите, нажмите «Готово».
```

Фотографии необязательны. На первом экране доступны кнопки `Пропустить` и `Отменить создание заявки`.

Правила MVP:

* максимум 5 фотографий на заявку;
* принимаются только Telegram photo messages;
* документы, PDF, видео, animation и другие файлы на этом шаге не принимаются;
* Telegram-альбом обрабатывается как несколько отдельных photo updates;
* бот не скачивает файлы через `getFile`;
* Telegram `file_id` временно хранится только в in-memory `WizardSession.photos`;
* `file_id` и `file_unique_id` не сохраняются в SQLite, админку и логи;
* при рестарте процесса незавершённая сессия и фотографии теряются.

После добавления фотографии бот отвечает:

```text
Фото добавлено: N из 5.
Можно отправить ещё или нажать «Готово».
```

После первой фотографии доступны кнопки `Готово`, `Очистить фото` и `Отменить создание заявки`. Кнопка `Пропустить` доступна только пока фотографий нет.

При шестой фотографии бот не добавляет её в сессию и сообщает, что достигнут лимит 5. Существующие фотографии не заменяются.

Кнопка `Пропустить` переводит заявку к предпросмотру без фотографий. Кнопка `Готово` переводит к предпросмотру с текущим списком фотографий. Кнопка `Очистить фото` удаляет все временные фотографии из сессии. На photo-step после очистки снова можно отправить новые фотографии или нажать `Пропустить`. В предпросмотре очистка обновляет только счётчик фотографий и кнопки, не вызывает DaData повторно и не меняет `formatted_card_text`.

## Позиции под замер

Сейчас доступны позиции:

* кухня;
* шкаф;
* ниша под шкаф;
* тумба под раковину;
* гардеробная;
* инсталляция;
* ТВ-зона;
* рабочая зона;
* стеновые панели;
* по плану;
* вписать вручную.

Пользователь может выбрать несколько позиций.

Кнопки и формы стандартной позиции для карточки берутся из общего справочника `src/services/measureServiceItems.ts`. Bot-layer использует wrapper/re-export из `src/bot/measureServiceItems.ts` для совместимости существующих импортов. В справочнике есть `buttonLabel`, `cardFirstLabel` и `cardListLabel`.

В кнопках используется именительный падеж. Первая позиция после слова "Замер" использует форму `cardFirstLabel`, например "кухни", "шкафа", "гардеробной". Вторая и последующие позиции в списке используют `cardListLabel`, например "кухня", "шкаф", "гардеробная".

Вариант "вписать вручную" просит менеджера ввести произвольный текст позиции; этот текст сохраняется в заявке как введённая позиция. Для ручного текста formatter применяет только базовые известные преобразования первой позиции, например "ниша над СМ" → "ниши над СМ"; пункты списка остаются в введённой форме.

## Обязательные позиции салона

Перед вопросами бот загружает активные `salon_required_items` для салона.

Если позиция активна и `auto_add_to_order = 1`, она автоматически добавляется в черновик.

Для таких позиций сохраняются snapshot-поля:

* `itemNameSnapshot`;
* `unitPriceSnapshot`;
* `priceTextSnapshot`;
* `cardTextSnapshot`;
* `isAutoAdded`;
* `source = salon_required_item`.

## Фиксированная оплата

В текущем коде используется:

* `default_payment_by`;
* `is_payment_by_fixed`.

Если `is_payment_by_fixed = 1` и задан `default_payment_by`, бот не спрашивает оплату, а сразу использует значение из салона.

Пример: `Settee` и `Тетрис Кухни` могут иметь фиксированную оплату салоном.

## Предпросмотр карточки

Перед сохранением бот пытается обогатить адрес через DaData, затем формирует карточку и показывает её пользователю.

Если DaData определила адрес как `OUT_MKAD` и у салона задан `mileage_price_per_km`, карточка показывает тарифную строку:

```text
Километраж от МКАД X₽/км.
```

В первой части карточки строка менеджера или директора формируется из snapshot-полей заявки. Если есть телефон и имя, сначала выводится телефон, затем имя без запятой и без принудительного переноса строки:

```text
роль: +7-XXX-XXX-XX-XX Имя
```

Если заполнен только телефон, выводится телефон. Если заполнено только имя, выводится имя. Если snapshot-поля менеджера отсутствуют, используется legacy `managerContact`.

Тарифные суммы в автоматически формируемой карточке отображаются с запятой как разделителем тысяч: `2500` выводится как `2,500₽`, диапазон `1000`-`1500` выводится как `1,000₽-1,500₽`, а значения меньше `1000`, например тариф километража `60`, остаются без разделителя: `60₽/км`. Это влияет только на новый текст карточки; числовые значения в SQLite, уже сохранённые `formatted_card_text` и snapshot-тексты обязательных позиций не пересобираются.

Если адрес внутри МКАД, DaData выключена, недоступна или не смогла определить адрес, строка километража не показывается. Создание заявки при этом не блокируется.

Фактическое расстояние от МКАД в карточке не выводится.

Действия:

* принять;
* очистить фото, если они были прикреплены;
* заполнить заново;
* отменить.

Предпросмотр содержит количество фотографий отдельно от карточки:

```text
Предпросмотр заявки
Прикреплено фото: N

<formatted_card_text>
```

Строка количества фотографий не входит в `formatted_card_text` и не отправляется как чистая карточка.

После принятия заявка сохраняется в SQLite со статусом `awaiting_coordination`.

Создание заявки, её позиций и initial history event выполняется атомарно:

```text
orders.status = awaiting_coordination
order_status_history.event_type = created
from_status_code = NULL
to_status_code = awaiting_coordination
```

После успешного сохранения менеджер получает базовое подтверждение:

```text
✅ Заявка #<id> принята.

Информацию о согласовании или переносе сообщим дополнительно.
```

После сохранения бот пытается отправить в dispatch-чат dispatch package в строгом порядке:

1. служебный заголовок заявки;
2. фотографии, если они были прикреплены;
3. чистый `formatted_card_text` без префиксов и без `parse_mode`, чтобы текст можно было скопировать как есть.

Первое сообщение начинается с фразы `О Повелитель, поступила новая заявка!` и содержит:

* номер заявки;
* салон;
* менеджера;
* дату замера;
* статус `ожидает согласования`;
* исходный адрес, введённый менеджером;
* нормализованный адрес DaData, если он есть;
* человекочитаемое расположение относительно МКАД/КАД или `Не определено`.
* примерное расстояние от МКАД, если DaData определила адрес как `OUT_MKAD` и вернула положительное расстояние.

Кнопки workflow добавляются только к служебному dispatch-заголовку:

```text
[✅ Согласовано] [📅 Перенесено]
```

Callback data:

```text
order:confirm:<orderId>
order:reschedule:<orderId>
```

Нажатие `✅ Согласовано` выполняет confirm flow только из настроенного закрытого dispatch-чата. Нажатие `📅 Перенесено` запускает in-memory reply-session переноса: сама кнопка заявку не меняет, business transition выполняется только после ввода новой даты и, если нужно, нового времени.

Строка `Примерное расстояние от МКАД: N км` показывается только для `OUT_MKAD`. Если адрес внутри МКАД, не определён или расстояние отсутствует, строка не показывается.

Последнее текстовое сообщение остаётся чистой карточкой для копирования. В него не добавляются служебный заголовок, DaData-блок, технические поля и фактическое расстояние от МКАД.

Если фотография одна, dispatch использует `sendPhoto` без caption. Если фотографий от 2 до 5, dispatch использует `sendMediaGroup` без captions. Карточка всегда отправляется отдельным последним сообщением, чтобы последним новым сообщением в рабочем чате был текст вида `На 14 июля...`, а не фотография.

Если отправка фотографий упала после успешного заголовка, бот всё равно пытается отправить чистую карточку. Dispatch-статус заявки остаётся `failed`, потому что пакет отправлен не полностью.

## Workflow согласования в рамках #6

Этот раздел описывает текущее поведение для Issues #9-#13. После Issue #10 DB foundation, client-agnostic `OrderWorkflowService` и workflow creation path уже есть. После Issue #11 Telegram runtime вызывает confirm flow. После Issue #12 Telegram runtime собирает ввод переноса через in-memory reply-session и вызывает `rescheduleOrder()` после полного ввода. После Issue #13 Telegram runtime выполняет post-commit side effects переноса. Текущий рабочий `/new` flow сохраняет новые заявки со статусом `awaiting_coordination` и создаёт history event `created`.

`OrderWorkflowService` умеет выполнять business transitions `confirmOrder()` и `rescheduleOrder()` через repositories и одну SQLite transaction. Telegram bot вызывает `confirmOrder()` для callback `order:confirm:<orderId>`. Для callback `order:reschedule:<orderId>` бот сначала собирает новую дату/время и только затем вызывает `rescheduleOrder()`.

Менеджер после создания получает сообщение о том, что заявка принята и информация о согласовании или переносе придёт отдельно.

Workflow controls размещаются на техническом dispatch header, а не на чистой карточке:

```text
[✅ Согласовано] [📅 Перенесено]
```

`formatted_card_text` остаётся чистым текстом карточки без workflow-кнопок, служебных header-полей и технических данных, чтобы его можно было копировать как раньше.

### Реализованный flow `✅ Согласовано`

После callback из закрытого dispatch-чата Telegram adapter:

1. подтверждает callback через best-effort `safeAnswerCbQuery()`;
2. парсит только `order:confirm:<orderId>`;
3. проверяет, что callback пришёл из `DISPATCH_CHAT_ID`;
4. перечитывает заявку из SQLite и для новых workflow-заявок сверяет `dispatch_notification_chat_id` и `dispatch_notification_header_message_id`;
5. вызывает `OrderWorkflowService.confirmOrder()` с actor context `source = telegram`, `externalId = Telegram user id` нажавшего кнопку;
6. после successful business commit уведомляет менеджера по `orders.telegram_user_id`;
7. редактирует существующий технический dispatch header на статус `согласовано` и убирает workflow-кнопки.

Менеджер после уведомления о согласовании ничего не подтверждает.

Уведомление менеджеру:

```text
✅ Заявка #<id> согласована.

Замер согласован на <дата>, <время>.
```

Если времени нет, текст отправляется без запятой и без `undefined`:

```text
✅ Заявка #<id> согласована.

Замер согласован на <дата>.
```

Ошибки уведомления менеджера или редактирования dispatch header не откатывают уже выполненный `confirmed` transition и не создают новую карточку.

### Реализованный input-flow `📅 Перенесено`

Callback `📅 Перенесено` не меняет заявку сразу. Он запускает отдельный reply-flow ввода новой даты.

Перед стартом session Telegram adapter:

1. подтверждает callback через best-effort `safeAnswerCbQuery()`;
2. парсит только точный формат `order:reschedule:<orderId>`;
3. перечитывает заявку из SQLite;
4. проверяет, что callback пришёл из `DISPATCH_CHAT_ID`;
5. для новых workflow-заявок сверяет `dispatch_notification_chat_id` и `dispatch_notification_header_message_id`;
6. проверяет, что текущий статус заявки ещё `awaiting_coordination`;
7. создаёт in-memory session по ключу `dispatchChatId + telegramUserId`.

Если у этого пользователя в dispatch-чате уже есть активная session, новая session не создаётся и бот отвечает:

```text
Перенос заявки #<id> уже начат. Введите новую дату или отмените перенос.
```

После успешного старта бот отправляет prompt:

```text
Введите новую дату замера для заявки #<id>.
```

К prompt добавляется inline-кнопка `Отменить перенос`. Бот сохраняет `message_id` этого prompt и принимает новую дату только если текстовое сообщение:

* пришло из настроенного `DISPATCH_CHAT_ID`;
* отправлено тем же Telegram user;
* относится к активной session этого user;
* является reply на актуальный prompt session.

Обычное сообщение dispatch-группы, не являющееся reply на актуальный prompt, не становится датой переноса и передаётся дальше по middleware chain.

Новая дата использует существующую validation/normalization logic `normalizeMeasureDateInput()`. Второй независимый parser даты не добавляется. Некорректная календарная дата не вызывает `rescheduleOrder()`: session остаётся активной, бот отправляет новый prompt даты с кнопкой отмены и обновляет ожидаемый `message_id`.

Новое время запрашивается только если у заявки раньше было заполнено `measure_time`. Если времени не было, перенос выполняется после ввода новой даты.

Старое время автоматически не переносится. Если старое `measure_time` было заполнено, после валидной даты бот спрашивает:

```text
Введите новое время замера для заявки #<id>.
```

Новое время остаётся свободным текстом и передаётся в `rescheduleOrder()` без отдельного parser-а.

После полного ввода Telegram adapter вызывает:

```ts
OrderWorkflowService.rescheduleOrder({
  orderId,
  newMeasureDate,
  newMeasureTime,
  actor: {
    source: "telegram",
    externalId: "<Telegram user id>"
  }
})
```

При `success` session очищается, а success result сервиса передаётся в post-commit handling вместе с Telegram context текущего header-а. Предыдущая дата/время берутся только из `RescheduleOrderResult`, а не из session или старого order adapter-а.

При `order_not_found` или `transition_not_allowed` session завершается контролируемо, post-commit hook не вызывается.

`Отменить перенос` удаляет session, не меняет заявку, не пишет `order_status_history`, не вызывает `rescheduleOrder()` и логирует безопасное событие `order_reschedule_cancelled`.

Незавершённая reschedule session хранится как in-memory MVP state. При restart процесса такая незавершённая сессия может потеряться, потому что business state заявки меняется только после вызова workflow service и успешного commit.

### Реализованный post-commit flow переноса

После successful `OrderWorkflowService.rescheduleOrder()` и SQLite commit Telegram runtime:

1. перечитывает актуальную заявку из SQLite;
2. редактирует существующую чистую dispatch-card актуальным `orders.formatted_card_text`;
3. обновляет существующий технический dispatch-header на новую дату и статус `ожидает согласования`;
4. сохраняет остальные строки header-а, включая салон, менеджера, фотографии и адресный блок;
5. возвращает на header workflow-кнопки `✅ Согласовано` и `📅 Перенесено`;
6. отправляет короткое служебное сообщение в dispatch-чат;
7. уведомляет менеджера через общий `ManagerNotificationService`.

Служебное сообщение в dispatch-чате формируется только из successful result business transition:

```text
📅 Заявка #4 перенесена
Было: 16 июля, после 16
Стало: 18 июля, с 14 до 16
Ожидает согласования.
```

Если времени нет, строки формируются без лишней запятой:

```text
📅 Заявка #4 перенесена
Было: 16 июля
Стало: 18 июля
Ожидает согласования.
```

Уведомление менеджеру:

```text
📅 Заявка #4 перенесена.

Новая дата замера: 18 июля, с 14 до 16.

Информацию о согласовании сообщим дополнительно.
```

Если времени нет, текст отправляется без запятой и без `undefined`.

Новая полная карточка в dispatch-чат при переносе не отправляется. `dispatch_notification_card_message_id` и `dispatch_notification_header_message_id` не меняются ни при успешных side effects, ни при ошибках Telegram.

Ошибки редактирования карточки, обновления header-а, отправки служебного сообщения или уведомления менеджера логируются как best-effort failures и не откатывают уже выполненный перенос.

## Работа в группе

В группе бот работает через команды и reply-сообщения.

Для текстовых шагов пользователь должен отвечать reply-сообщением на вопрос бота. Это нужно, чтобы flow работал даже при включённом Telegram privacy mode.

Кнопочные шаги работают через inline-кнопки.

## Что бот пока не делает

На MVP бот не делает:

* AI-парсинг произвольных сообщений;
* webhook;
* интеграции с другими мессенджерами;
* расчёт итоговой стоимости.
